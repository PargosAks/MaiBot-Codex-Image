# 已有作品推进修复（0.12.1）

## 问题与边界

0.12.0 的 Host 每 5 秒检查 worker，但创建计划、生成、取图、评审、分享都依赖原有 wake；`idle_seconds=3600` 时，一幅已完成的图也要等下一小时才能取图，再下一小时评审。MCP 完成通知没有接入这条流程。修复只改插件，不改 MaiBot、MCP、数据库 schema、现有配置或预算。

## 技术方案

`Artist.tick()` 保留原空闲调度，同时调用 `ArtistStore.schedule_progress_wake()`。后者在 SQLite 事务内确认授权、退避、现有 claim/待消费 wake 和作品状态，只为既有作品写入内部 completion 事件。签名绑定作品和阶段，持久时间戳约束同阶段至少间隔 15 秒；查回执和成品规划是不同阶段，可在下一 tick 继续。入队与消费仍使用既有持久队列及 claim，不使用仅进程内的完成标记。重启优先恢复未确认推进批次的原 watermark，避免后来到达的 idle/chat 改变规划幂等键。

原图运行中只查询原请求或 job；有图片后沿用校验、落盘和评审。对已评审且尚未作后续规划的作品及时询问模型一次，是否分享仍由它决定；已有分享操作或已作后续规划的历史作品不因此重复唤醒。结果未知的旧 render 可继续只读核对，但不能重新生成或重新发送。

模型 wait、defer、失败退避和原授权/预算照常约束。成品候选复用当前授权、绑定及最佳版本的有效接受证据，旧授权的 review 不触发付费规划。已知 blocked 返回补充 300 秒退避，避免短周期模型空转；原任务有图但仍正常运行且占满并发槽时继续查询原回执，结算后再申请评审。纯内部推进唤醒不能创建另一幅作品；没有既有作品时，仍按原 `idle_seconds` 思考。
